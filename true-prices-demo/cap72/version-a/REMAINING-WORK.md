## 1. XDR, everywhere that decodes an `AccountEntry`

The new `SignerKey` arm is in a ledger entry, so anything that decodes accounts (not just anything that builds the new op) breaks on the first account that carries one. The gate `CAP_0072_DELEGATED_SIGNERS` in `patches/stellar-xdr.patch` has to be turned on in each generator.

- `stellar/stellar-xdr`: apply `patches/stellar-xdr.patch` on a branch. Decide the open points in HOST-PATCH.md (result code value, `SCAddress` vs `Hash`, where `SignerKey` can see `SCAddress` for `xdrc`). Small.
- `stellar/rs-stellar-xdr`: `patches/rs-stellar-xdr.patch`, plus `make generate` for `xdr-json/`, `xdr-definitions-json/` and `xdr-version` once the submodule points at the branch. Mostly generated.
- Go: `stellar/go-stellar-sdk` (`go.mod` module used by both stellar-rpc and stellar-horizon, `v0.7.2`) generates `xdr/xdr_generated.go` from `XDR_COMMIT=9c9c1459…` with xdrgen (`Makefile` lines 19 to 60, target `xdr`). Point `XDR_COMMIT` at the branch and regenerate; xdrgen must be run with the feature defined (how xdrgen takes ifdef defines was not checked, (inference)). Then hand-written code: `xdr/signer_key.go` `GetAddress` returns `unknown signer key type` for anything but the four arms (line 55 in `stellar/go`'s copy; same file in the SDK), and `xdr/signers.go`. Under the contracts-only rule the new arm renders as the C strkey. Small, mostly generated.
- JS: `stellar/js-stellar-base` generates `src/generated/curr_generated.js` and `types/curr.d.ts` with xdrgen from `xdr/curr/*.x` (`Makefile` lines 1 to 80; `XDR_BASE_URL_CURR` pins stellar-xdr commit `cff714a…`; `next_generated.js` exists for exactly this purpose). Then `src/signerkey.js` `encodeSignerKey`/`decodeAddress` (lines 55 to 93 throw on an unknown type), `src/operations/set_options.js` to accept a contract signer (`opts.signer.ed25519PublicKey | preAuthTx | sha256Hash | ed25519SignedPayload` today, lines 36 to 130). `@stellar/stellar-sdk` re-exports base, so the demo pins both through npm `overrides` (spec, version A section). Medium, about 100 lines plus generated.
- Rust tooling that uses `rs-stellar-xdr`: see Stellar CLI below.

## 2. stellar-core

All in `src/transactions/`, behind `protocolVersionStartsFrom(ledgerVersion, <next>)` like the `V_19` signed-payload checks, built with `--enable-next-protocol-version-unsafe-for-production` (`configure.ac` lines 605 to 615; `src/Makefile.am` line 86 maps it to `--features next` for the host). The XDR headers are generated by `xdrc` from the `src/protocol-curr/xdr` submodule (`src/Makefile.am` lines 116 to 122; `XDR_FEATURE_FLAGS` on line 117 is empty today and is where `-DCAP_0072_DELEGATED_SIGNERS` would go under the next-protocol conditional).

1. `SetOptionsOpFrame.cpp::doCheckValid` (lines 231 to 325): accept `SIGNER_KEY_TYPE_SC_DELEGATED` when the protocol is new enough and the payload is a contract address (contracts-only rule); otherwise `SET_OPTIONS_SIGNER_TYPE_NOT_SUPPORTED` (new code) or `SET_OPTIONS_BAD_SIGNER` before the protocol. The existing `isSelf`/`isPublicKey` checks (lines 288 to 300) use `KeyUtils::canConvert<PublicKey>`, which must not panic on the new arm. `addOrChangeSigner` (lines 45 to 100) and `deleteSigner` are type-agnostic (`findSignerByKey`, sorted insert, sponsorship bookkeeping) and should need no change beyond the comparison operators the new union arm gets for free. About 40 lines plus tests in `test/SetOptionsTests.cpp`.
2. `SignatureChecker.cpp::checkSignature` (lines 50 to 165) splits signers by `key.type()` into a map and only looks up the four known types, so delegated signers are already ignored for transaction signatures. Add a test that a delegated signer never contributes weight; `SignatureUtils.cpp` and `KeyUtils` need to tolerate the arm (hint matching, `convertKey`). About 20 lines plus tests. The CAP's `TransactionFrame::checkSignature` wording maps to these two files.
3. `TransactionFrame.cpp` extraSigners: `checkExtraSigners` (lines 459 to 482) and the precondition validation (lines 1276 to 1296, which already rejects an empty signed payload with `txMALFORMED`). Add: a `SIGNER_KEY_TYPE_SC_DELEGATED` extra signer fails validation with `txACCOUNT_DELEGATED_SIGNER_NOT_SUPPORTED`. About 15 lines plus a test in `test/TxEnvelopeTests.cpp`.
4. Host bump: `src/rust/Cargo.toml` `[dependencies.soroban-env-host-p30]` (line 118, `rev = "6e6c4a8…"`, `features = ["next"]`) and the matching `src/rust/soroban/p30` submodule (`.gitmodules`) point at the host fork, with `rs-stellar-xdr` patched in through the fork's `Cargo.toml` (the host fork would need a git dependency rather than the path patch used here). `src/Makefile.am` lines 240 to 260 (`WIP_SOROBAN_PROTOCOL`, `SOROBAN_FEATURE_NEXT`) decide whether `--features next` is passed; no change if the fork stays labeled p30.
5. `InvokeHostFunctionTests.cpp`: an end-to-end test that a G-account with a delegated signer authorizes a Soroban invocation, like the CAP-71 tests (PR 5272 was about 400 lines of tests for CAP-71).
6. Nothing in `src/ledger` for the GAC, reserves or sponsorships, by the CAP-72a scope.

Estimate: 300 to 600 lines including tests; the build is the expensive part. Needs a core engineer.

## 3. stellar-rpc

Verified: RPC embeds the host for simulation. `cmd/stellar-rpc/lib/preflight/Cargo.toml` depends on `soroban-env-host-curr`/`-prev` and `soroban-simulation-curr`/`-prev` (lines 19 to 22), selected by ledger protocol in `lib/preflight/src/lib.rs` (`PROTOCOL = soroban_env_host::meta::INTERFACE_VERSION.protocol`, lines 37 to 70; unsupported protocol bails at lines 211 to 265). Workspace pins are in the root `Cargo.toml` lines 21 to 40 (`curr` = 29.0.1 from crates.io, `prev` = 28.0.1 by git rev; `stellar-xdr` 28.0.0 with `serde,type_enum`).

- Point `soroban-env-host-curr` and `soroban-simulation-curr` at the host fork by git rev, with `features = ["next"]` added, and `stellar-xdr` at the XDR fork with `cap_0072_delegated_signers`. The two-host arrangement means the protocol selection in `lib.rs` has to accept protocol 31 from the `curr` host.
- Go side: bump `github.com/stellar/go-stellar-sdk` (`go.mod` line 26) to the regenerated XDR, or `getLedgerEntries`/ingestion fail to unmarshal an account with the new signer (inference: Go XDR decoding of an unknown union discriminant is an error).
- `xdr2json` (`cmd/stellar-rpc/lib/xdr2json`) uses `stellar-xdr` with `type_enum`; it follows the crate bump.

Estimate: dependency bumps plus a protocol-selection tweak, under 100 lines; the Rust rebuild is slow.

## 4. Stellar CLI and Lab

- `stellar/stellar-cli` uses `stellar-xdr` 28.0.0 and `soroban-env-host` 28.0.2 (`Cargo.toml` lines 45 to 52), so it lags the host by two versions and can't decode the new arm. `tx new set-options --signer` takes an `UnresolvedMuxedAccount` and `resolve_signer_key` (`cmd/soroban-cli/src/commands/tx/args.rs` lines 171 to 180) maps only `PublicKey` to `SignerKey::Ed25519`. Adding a `--signer` that accepts a `C...` address and produces `SignerKey::ScDelegated` is about 30 lines once the crate is bumped; account display (`keys`, `tx` decoding) follows the crate. The spec keeps the CLI out of version A and builds the `SetOptionsOp` in the runner with the patched JS SDK; step 1's classic payment still works with the stock CLI.
- Stellar Lab (`stellar/laboratory`) uses js-stellar-sdk; it decodes accounts and builds `SetOptions` from the same `signerkey.js` paths, so it follows the JS SDK patch, plus a form field for the new signer type. Not needed for the demo.

## 5. Horizon

Horizon lives in `stellar/stellar-horizon` (module `github.com/stellar/stellar-horizon`, depends on `go-stellar-sdk v0.7.2`). It ingests account signers in `internal/ingest/processors/signers_processor.go` (file exists at that path on main; contents not read) and renders them as `protocols/horizon.Signer{Weight, Key, Type, Sponsor}` through `SignerKey.GetAddress`, which errors on unknown types. With the Go XDR regenerated and `GetAddress` returning the C strkey, the new signer shows up with `type: "sc_delegated"` or similar (name to pick). About 50 lines plus the SDK bump.

For the demo it is simpler to not run Horizon, and quickstart allows that: `start` line 33 defaults `ENABLE` to `core,horizon,rpc`, `--enable core,rpc` leaves Horizon out (`ENABLE_HORIZON` stays `false`, line 36), and friendbot is still configured, against RPC rather than Horizon (`init_friendbot`, lines 544 to 560: with `ENABLE_RPC=true` it writes `rpc_url = "http://localhost:8003"` and `fund_contract_addresses = true` into `friendbot.cfg`). The README's line 188 ("horizon is run when rpc is requested so that friendbot is available") describes older behavior (inference). So the demo runs `--enable core,rpc`, funds accounts through friendbot, and reads all state through RPC. If Horizon is wanted anyway, the `future` entry's `horizon_skip_protocol_version_check` lets it start, but its ingestion fails at the first account that carries a delegated signer until the Go XDR is regenerated.

## 6. Quickstart image

`images.json` is a list of tagged entries, each with `config` and `deps` (`xdr` = rs-stellar-xdr, `core`, `rpc`, `horizon`, `friendbot`, `lab`, `galexie`); `make build TAG=<tag>` (`Makefile` lines 5 to 50) resolves the entry into `.image.json` and runs `docker build`. The `future` entry is the template: core `configure_flags: "--disable-tests --enable-next-protocol-version-unsafe-for-production"`, `protocol_version_default_autoupdate: false`, `horizon_skip_protocol_version_check: true`.

Add an entry:

```json
{
  "tag": "cap72",
  "events": [],
  "config": { "protocol_version_default": 31, "protocol_version_default_autoupdate": false,
              "horizon_skip_protocol_version_check": true },
  "deps": [
    { "name": "xdr",  "repo": "<fork>/rs-stellar-xdr", "ref": "<branch>" },
    { "name": "core", "repo": "<fork>/stellar-core",   "ref": "<branch>",
      "options": { "configure_flags": "--disable-tests --enable-next-protocol-version-unsafe-for-production" } },
    { "name": "rpc",  "repo": "<fork>/stellar-rpc",    "ref": "<branch>" },
    { "name": "horizon", "repo": "stellar/stellar-horizon", "ref": "<a recent ref>", "options": { "pkg": "github.com/stellar/stellar-horizon" } },
    { "name": "friendbot", "repo": "stellar/friendbot", "ref": "4a6a1715d5b81c640dd9f887dd37b26499e95e72", "options": { "pkg": "github.com/stellar/friendbot" } },
    { "name": "lab", "repo": "stellar/laboratory", "ref": "main" },
    { "name": "galexie", "repo": "stellar/stellar-galexie", "ref": "galexie-v28.0.0" }
  ],
  "tests": { "continue-on-error": true, "additional-tests": [] }
}
```

The `xdr` dep builds the `stellar-xdr` CLI binary into the image (`Dockerfile` lines 23 to 37 and 237), used for decoding; it should be the fork so `stellar-xdr decode` understands accounts. Whether `protocol_version_default` may exceed what the image's config-settings directories cover is handled by `start` lines 355 to 370 (falls back to the nearest lower `p<N>` config dir).

Build and run:

```bash
make build TAG=cap72
docker run --rm -p 8000:8000 stellar/quickstart:cap72 --local --protocol-version 31 \
  --enable core,rpc --enable-soroban-diagnostic-events
```

`--protocol-version` is documented for `--local` (README line 135); `--enable` takes a comma list (lines 168 to 188); `--enable-soroban-diagnostic-events` is applied to both captive core configs (`start` lines 584 and 617). Protocol 31 is what the `next` host labels itself (`soroban-env-macros/src/lib.rs`, `LEDGER_PROTOCOL_VERSION = 31` under `next`), so the ledger must be upgraded to 31 for the host's runtime gate to open; the image's upgrade flow handles that from `PROTOCOL_VERSION`.

## 7. The demo itself (`version-a` runner)

Already planned in the spec and ARCHITECTURE.md: `SetOptionsOp` with the contract signer built from the patched JS SDK; signer that emits `SorobanCredentialsAddressWithDelegates` with `scvVoid` on top and one delegate `{ address: agent_policy, signature: AgentSignature, nestedDelegates: [] }` over the `ENVELOPE_TYPE_SOROBAN_AUTHORIZATION_WITH_ADDRESS` preimage; facilitator subclass that accepts that credential type and a local network entry for `@x402/stellar`. The host tests in this patch show the exact entry shape (`build_auth_entry` in `soroban-env-host/src/test/account_delegated_signers.rs`). Per the departures in HOST-PATCH.md, the runner should refuse to build a `SetOptionsOp` with a G-address delegate, and print "delegated signers can't change this account's signers or thresholds" next to the signer table.
